# Relay historical purchase discovery — implementation foundation

## What is implemented
- Pure matching core with a continuously extensible identifier registry.
- Configurable 60-day historical lookback and candidate scoring.
- Hard conflicts on currency, amount and card details (when both sides supply them).
- Shared processor references identified as stronger evidence.
- **No candidate is treated as verified ownership and no refund is unlocked.**
- Node tests: `node identity/purchase-identity.test.mjs`.

## Data source realities
Bank feeds usually provide transactions, not basket line items. Card last-four is optional and cannot prove ownership. Square payment identifiers do not automatically appear in bank data. Retailer orders require merchant authorisation or customer-authorised access. The current Square/Plaid Sandbox purchase is generated by Relay and is not independent historical matching.

## Next implementation gates

2. Add authenticated consumers and secure bank consent/token storage. **Do not reuse brand+last4 or orderId URL query parameters as authorisation.** Existing verified feed is Sandbox-only and is not production-safe.
3. Build Square multi-merchant OAuth and historical order backfill with pagination; then Shopify authorised merchant app and historical backfill.
4. Build Plaid/TrueLayer transaction backfill and incremental webhook processing with idempotency and consent expiration.
5. Run this matching module against independently ingested records, handle many-to-one, refunds, split tenders, pending vs posted, timezone and duplicate amounts.
6. Add secure customer-assisted claims: order number is a locator, not a secret. Verify with retailer-authorised API plus authenticated customer proof before exposing line items or enabling refund eligibility.
7. Collect metrics: candidate coverage, independently verified precision, false-positive rate, latency, unmatched reasons.

## Identifier discovery discipline
For each new provider payload, inventory field names, provenance, whether stable across systems, coverage, sensitivity and retention. Never store full card PAN/CVV. Add supported fields to registry only after confirming real availability. Log **field presence** and match outcomes, not raw sensitive payloads. Track conflicts and missing identifiers explicitly.

## Product definition
A universal wallet is an aspiration; initially support verified purchases from participating merchants, plus bank-only potential purchases. No historical customer purchases are automatically accessible merely because a Square merchant is integrated.
